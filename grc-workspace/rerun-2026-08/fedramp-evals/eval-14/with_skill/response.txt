## 7.1 Authorization Boundary Overview

The authorization boundary for [System Name] ("the System") encompasses all components that process, store, or transmit federal information within the CSP's production environment hosted on **AWS GovCloud (US)**. The System is delivered as a **Software as a Service (SaaS)** offering in a **public cloud deployment model**, categorized at the **FedRAMP Moderate (Certification Class C)** baseline.

The boundary includes the following in-scope components:

| Component | Role | In/Out of Boundary |
|---|---|---|
| Web application tier | Application logic, request handling, presentation layer | In boundary |
| PostgreSQL database | Primary system of record; stores federal data | In boundary |
| Redis cache | Session state / application caching layer | In boundary |
| Load balancers / API gateway | Ingress traffic management, TLS termination | In boundary |
| Logging / SIEM aggregation | Centralized audit log collection (AU family) | In boundary |
| AWS GovCloud infrastructure (compute, network, storage) | Underlying IaaS | In boundary; PE and select SC controls inherited from AWS GovCloud (FedRAMP High authorized) |
| Okta (authentication/identity provider) | External SaaS — user authentication, SSO, MFA enforcement | **Interconnection — see 7.3** |
| SendGrid (transactional email) | External SaaS — outbound system-generated email (notifications, password resets, alerts) | **Interconnection — see 7.3** |

All components that process, store, or transmit federal data reside within AWS GovCloud region boundaries; standard (non-GovCloud) AWS commercial endpoints are explicitly excluded from use to avoid inadvertently placing federal data outside the authorization boundary.

**Action items to close before this section is finalized (flag these — they are the most likely 3PAO/PMO findings for this boundary):**
1. Confirm whether Okta and SendGrid instances used are their FedRAMP-authorized government offerings or standard commercial products. Standard commercial instances connected to an in-scope system are a common finding unless data flows are minimized and documented with compensating controls.
2. Determine whether any federal data (including PII) transits or is stored by SendGrid via email content — this affects both boundary treatment and whether a Privacy Impact Assessment (SSP Appendix Q) is triggered.
3. Document Interconnection Security Agreements (ISAs/MOUs) for both Okta and SendGrid regardless of authorization status.
4. Confirm all administrative/management traffic (e.g., DevOps access to AWS GovCloud, database admin access) is captured in the data flow diagram — omitted admin traffic is one of the most common SSP findings.
5. Document DNS, NTP, and any other infrastructure-support external services used by the System, even if seemingly trivial — these are frequently missed and flagged.

## 7.5 Encryption

All federal data must be encrypted at rest (PostgreSQL, Redis where applicable) and in transit (all connections, including to Okta and SendGrid) using FIPS 140-2/3 validated cryptographic modules. Document each module in the Cryptographic Modules Table (SSP Appendix L). Confirm Redis is not used to cache any federal data unencrypted in memory beyond what's operationally necessary, and document key management procedures.

## 7.6 Inherited Controls

Because the System runs on AWS GovCloud (FedRAMP High authorized), a substantial share of **Physical & Environmental (PE)** controls and select **System & Communications Protection (SC)** controls are inherited. Document the specific inherited controls, and the CSP's portion of any hybrid controls, in the **CIS/CRM workbook (SSP Appendix I)**. Do not describe fully-inherited controls as CSP-implemented in the control narratives — reference the CIS/CRM workbook instead.
